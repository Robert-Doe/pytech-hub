The Array

The first real data structure this course builds — and the proof that "random access is O(1)" isn't a rule to memorize, it's a direct consequence of Module 01's address arithmetic.

What this module proves, in one line

Because every element's address is base + index × element size, reaching element 4 costs exactly the same as reaching element 4,000,000 — and because that address math only works inside a fixed block of memory, this array cannot grow past the size it was given.

01

The Big Analogy

A parking garage with numbered, identically-sized spaces. Imagine a single-level parking garage with exactly 8 spaces, numbered 0 through 7, each exactly one car wide. If I tell you "the red car is in space 4," you can walk directly to space 4 without checking spaces 0 through 3 first — you just count four car-widths from the entrance. That's random access: knowing the index is enough to compute the location, with no searching involved.

But notice what that convenience costs you: the garage has exactly 8 spaces, painted and poured in concrete. You cannot wish a 9th space into existence — there's a wall there. If you need to park a 9th car, this garage, as built, cannot help you. That limitation isn't a bug in the garage's design; it's the direct price of every space being a fixed, predictable distance from the entrance. Module 03 is what happens when you ask "what if we could move to a bigger garage automatically, mid-parking-trip?"

02

What Happens, Step by Step

  1. A FixedArray is created with room for exactly 8 ints, laid out contiguously (Module 01's stride guarantee) — in C and C++, this space lives on the stack, sized at compile time.
  2. push(value) writes into the next free slot (data[length]) and increments length — an O(1) operation, since it never needs to look at any other slot.
  3. get(index) first checks 0 <= index < length. If it fails, the call reports failure (a return code, an exception, or an exception, per-language — see DECISIONS.md #1) instead of reading memory that isn't actually in use.
  4. If the check passes, get computes the address &data[0] + index directly — no loop, no searching — and reads the value there. This is the entire mechanism behind "O(1)."
  5. push past the 8th slot is rejected the same way an out-of-bounds get is: the capacity check fails, and the structure reports it cannot comply, rather than silently overwriting memory it doesn't own.

04

The Code, Explained

The bounds check that makes O(1) access safe

c/fixed_array.c 
int array_get(const FixedArray *arr, size_t index, int *out_value) {
    if (index >= arr->length) {
        return 0; /* out of bounds: caller asked for a slot not in use */
    }
    *out_value = arr->data[index];  /* one address computation, one read */
    return 1;
}

The check costs O(1) too — it's a single comparison, not a scan — so it doesn't change the overall complexity of get. What it buys is real: an invalid index fails loudly instead of reading whatever bytes happen to sit past the array in memory.

Same check, three different ways of saying "no"

cpp/fixed_array.cpp — throws 
int FixedArray::get(std::size_t index) const {
    if (index >= length_) {
        throw std::out_of_range("FixedArray::get: index out of range");
    }
    return data_[index];
}
python/fixed_array.py — raises 
def get(self, index):
    if not (0 <= index < self._length):
        raise IndexError(f"FixedArray index {index} out of range (length={self._length})")
    return self._data[index]

Same logical check (index must be a currently-used slot), three different failure-reporting mechanisms — each one matching what that language's own standard library already does for the identical situation. See DECISIONS.md #1 for why this isn't arbitrary.

Why capacity can't just be a constructor argument

cpp/fixed_array.hpp 
constexpr std::size_t kFixedArrayCapacity = 8;  // compile-time, not runtime

class FixedArray {
    int data_[kFixedArrayCapacity];   // stack storage -- size must be known here
    std::size_t length_;
    ...

A runtime capacity would force data_ onto the heap — which this course deliberately holds off on until Module 03. See DECISIONS.md #5.

Limits / What You Cannot Do Yet

Can't do yet

  • Grow past the capacity you started with — a 9th push always fails, by design
  • Insert or delete in the middle without writing that logic yourself (this module only appends)
  • Choose a capacity at runtime without moving the array to the heap (Module 03)
  • Reason formally about why get() is "O(1)" rather than just observing that it looks fast (Module 04)

07

Brain Exercise

Work through this before revealing the answer:

This module's get() and a hypothetical "search for the first value equal to 40" function would both eventually return the value 40. Are they the same complexity? Why or why not?

No — and the difference is the entire point of this module. get(4) is told exactly which slot to read, so it goes straight there: one comparison (bounds check), one address computation, one read — O(1), regardless of which index is requested or how many elements are in use. A "find the value 40" function is told a value, not a location, so in the worst case (the value is last, or absent) it must inspect every slot in order — O(n). Both return "40," but one was handed the address as an index and the other had to discover it. This exact distinction — knowing where vs. having to look — is what separates every O(1) operation in this course from every O(n) one you'll meet starting with linear search in Module 37.

08

There Are No Dumb Questions

Why is Python's get/set API here, when real Python code just writes arr[i]?

Because this module's whole purpose is to make the mechanism explicit rather than let square-bracket syntax hide it. arr[i] in real Python calls a special method (__getitem__) that could, in principle, do exactly what get() does here — this course just isn't ready to introduce Python's "dunder" method protocol yet, so the bounds-checking logic is a plain named method instead. Nothing about the underlying idea changes.

The C demo leaves data[] uninitialized. Isn't reading uninitialized memory undefined behavior?

Reading it directly, yes — but nothing in this module's public API lets a caller do that. Every read goes through array_get, which refuses any index >= length, and length only ever grows one slot at a time as push writes into it. So the uninitialized tail of data[] is never reachable through this module's own functions — see DECISIONS.md #2 for why we chose not to pay to zero it anyway.

Could this module's array just use std::array<int, 8> in C++ instead of a raw int[8]?

Yes, and idiomatic modern C++ would. We used a raw array here specifically so the C and C++ versions stay structurally close enough to compare line-for-line — once that comparison has done its job, later C++ modules lean on standard-library types more freely. This is a deliberate, one-time teaching tradeoff, not a recommendation to avoid std::array in real code.

If capacity is fixed at 8 everywhere, how would I ever use this for real data?

You wouldn't, on purpose — that's not a flaw this module missed, it's the exact wall Module 03 exists to knock down. Everything you've verified here (contiguous layout, O(1) access, a hard capacity limit) is still true of the dynamic array Module 03 builds; the only thing that changes is what happens the instant that limit is hit.
