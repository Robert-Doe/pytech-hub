Prerequisite 01 of 04

Variables & Memory

What a variable actually is once the compiler or interpreter is done with it — and the two very different places a value can live.

01

The Big Analogy

A row of numbered post office boxes. Picture your computer's memory as one enormous wall of numbered post office boxes — box #1, box #2, box #3, all the way up into the billions. Every box is exactly one byte wide. A variable is not the value inside a box — it's a label you stuck on the outside of a box (or a run of boxes), so you don't have to remember "the thing I care about is in box #4,481,204." When your code says x = 5, you're not creating the number 5 out of nowhere — you're writing 5 into some box(es) and taping a label reading "x" onto them.

Two different clerks manage this wall of boxes, and they work very differently: one is fast, disciplined, and only rents boxes in a strict line; the other is slower, more flexible, and will rent you a box of any size for as long as you ask. Those two clerks are the stack and the heap.

02

What Happens, Step by Step

  1. You declare a variable (e.g. int x; in C, x = 5 in Python). The runtime reserves enough boxes to hold that kind of value.
  2. The reservation happens in one of two places. Local variables with a size known at compile time (like a single int) go on the stack — a strictly ordered region that grows and shrinks automatically as functions are entered and exited. Anything whose size isn't known until runtime, or that needs to outlive the function that created it, goes on the heap — a large, unordered region you must explicitly ask for space in (and, in C/C++, explicitly give back).
  3. The variable name is resolved at compile/parse time to "box(es) starting at this address." From then on, using the variable is really the compiler silently inserting "read/write starting at that address" for you.
  4. When the variable goes out of scope, stack space is reclaimed automatically (the clerk just marks those boxes "next in line" again — nothing is erased, just no longer labeled). Heap space is not automatically reclaimed in C/C++ — you must call free() / delete, or it stays rented forever (a memory leak). Python's heap is managed for you by a garbage collector — a different mechanism, but the stack/heap split here still describes where the object itself lives.
03

A Concrete Map of State

Stack ↓ (one running function)

  1. int x = 5;@0x7ffee01
  2. int *p = &x;@0x7ffee09
  3. char name[4]4 boxes

Freed automatically when the function returns. Fixed size, known at compile time.

Heap (scattered, on request)

  1. 10 ints@0x55f10
  2. 40 bytes@0x55fa0

Size decided at runtime (malloc/new/list()). Lives until explicitly freed (or garbage-collected in Python).

The highlighted row: p doesn't hold 5 — it holds the address 0x7ffee01, i.e. "go look at x." That indirection is the whole subject of the next page.

One confusion to kill early

"The stack" here (a region of memory every running function uses) is a completely different thing from "a Stack" the data structure you'll build in Module 07. They share a name because they share a LIFO (last-in-first-out) shape — the call stack really is a stack data structure, just one the CPU/runtime manages for you instead of one you build yourself. This course keeps them apart in the glossary as Stack (memory) vs Stack (ADT).
