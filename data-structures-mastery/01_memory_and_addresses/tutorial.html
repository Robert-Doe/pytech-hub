Memory & Addresses

Every data structure this course builds is, underneath, just a naming scheme over raw addressable memory. This module proves that claim with real, running code instead of asserting it.

What this module proves, in one line

A variable name is a label on a memory address — and once you can hold that address itself (a pointer/reference), you can hand a function the power to modify the caller's variable, or walk a run of values one address at a time.

01

The Big Analogy

A hotel with numbered rooms, and a hotel with numbered rooms whose front desk also sells you a card telling you which room someone else is in. An ordinary variable is a guest in a room — box #4,481,204, say. You (the program) know the guest's name ("x") and the room number is handled for you.

A pointer is a different kind of purchase entirely: a small index card that says "the guest you want is in room #4,481,204." The card itself lives in some other room — it has to, it's a physical object too. Handing someone that card doesn't hand them the guest. It hands them directions. But directions are exactly what a function needs if you want it to knock on that door and change something about the guest inside — which is a power a plain copy of the guest's name would never give it.

02

What Happens, Step by Step

  1. A variable is declared. The compiler (C/C++) or runtime (Python) reserves space and silently remembers "this name means: start reading/writing at this address."
  2. Taking that variable's address (&x in C/C++; implicit in Python) produces a new, separate value — the address itself — small enough to fit in one machine word, regardless of how large the thing it points to is.
  3. That address can be stored in its own variable (a pointer, or a C++ reference, or just any Python name) and passed to a function.
  4. Inside that function, dereferencing the address (*p in C/C++; implicit in Python) reads or writes the original variable — not a copy — because the address was never a copy to begin with.
  5. For an array, this generalizes: each element's address is the previous element's address plus one element's size, exactly, with no gaps — which is what array_stride_bytes in this module's code measures and proves.

04

The Code, Explained

Proving the stride (all three languages agree)

c/memory_and_addresses.c 
ptrdiff_t array_stride_bytes(const int *arr) {
    /* Cast to char* first: pointer subtraction on int* reports
       "how many ints apart," not "how many bytes apart." */
    return (const char *)&arr[1] - (const char *)&arr[0];
}

The cast to char * is not stylistic — see DECISIONS.md §2 for why the C standard forces it. In C++, the same function uses reinterpret_cast<const char *> instead of a C-style cast — same operation, spelled the way C++ prefers when changing a pointer's type without changing what it points at.

Swap by address vs. swap by mutation (three languages, one idea)

c/memory_and_addresses.c — swap via pointer 
void swap_ints(int *a, int *b) {
    int temp = *a;   // read through the address
    *a = *b;         // write through the address
    *b = temp;
}
cpp/memory_and_addresses.cpp — swap via reference 
void swap_ints_ref(int &a, int &b) {
    int temp = a;    // no * needed -- the compiler dereferences for you
    a = b;
    b = temp;
}
python/memory_and_addresses.py — swap via shared-object mutation 
def swap_via_temp(lst, i, j):
    # lst is a reference the caller already holds too --
    # mutating it here is visible to the caller, with no & needed
    lst[i], lst[j] = lst[j], lst[i]

All three achieve the identical outcome — the caller sees the swap — through the same underlying mechanism (mutate through a shared address), spelled three different ways. Why Python's version takes a list and two indices instead of two bare values is explained in DECISIONS.md §7 — it's not a style choice, it's the only version that actually works.

Getting a blank or broken result?

Address values will not match the ones printed above — that's expected, not a bug. Addresses are assigned fresh by the OS on every run and depend on your machine, your OS, and even ASLR (address space layout randomization). What must match: p's printed value and &x's printed value should be identical to each other (just not to the numbers above), the stride should always be 4 on a system where sizeof(int) == 4, and both test runners must print their "All ... tests passed." line with no assertion failures. If gcc/g++ isn't found, this course assumes a standard C11/C++17 toolchain is on your PATH — install one (e.g. via your OS package manager, or WSL/MinGW on Windows) before continuing.

07

Brain Exercise

Before revealing the answer, work through this on paper:

In C, swap_ints(&x, &x) — passing the SAME variable's address as both arguments — what happens, and why is it safe?

Trace it: temp = *a reads x's current value into temp. *a = *b writes x's value into... itself (since a and b are the same address) — no change. *b = temp writes the saved original value back into x — also no change. Net effect: x ends exactly where it started. It's safe specifically because every step reads before it overwrites — nothing is lost before it's saved. This is actually asserted directly in test_memory_and_addresses.c: swap_ints(&c, &c); assert(c == 42);. Contrast this with an in-place algorithm that doesn't save a temp first — that's a real bug class you'll meet again once Module 34 (Quick Sort) starts swapping array elements by index.

08

There Are No Dumb Questions

Why does Python print an id() that looks exactly like a C address, if the language spec says it's not guaranteed to be one?

Because you're running CPython, and CPython's particular implementation of id() really is "return the object's memory address" — that's an implementation choice CPython made, not a promise the Python language makes. See DECISIONS.md §6. Another Python implementation (PyPy, for instance) is free to return something else entirely and still be 100% correct Python.

If a C++ reference is "just a safer pointer," why does this course use raw pointers at all after this module?

It doesn't, mostly — but this module deliberately shows both so you can watch them do the identical thing side by side (DECISIONS.md §4). From Module 05 onward, the C++ implementations still use raw pointers for one specific reason: a linked structure's node has to be able to point at nothing (the end of a list), and a C++ reference — unlike a pointer — can never be null. That's not this module's problem yet, but it's why the choice isn't "always prefer references."

Why did array_stride_bytes return exactly 4, and will it always?

4 because this module's demo used int, and on the machine this was run on (and the overwhelming majority of modern desktop/server systems), sizeof(int) == 4. It is not a language guarantee — the C standard only requires int be at least 16 bits, and some embedded platforms differ. The test file doesn't hardcode 4 for exactly this reason — it asserts array_stride_bytes(arr) == sizeof(int), which is true regardless of what sizeof(int) happens to be on the machine running it.

The demo prints the addresses of local variables. Is it safe to save one of those addresses and use it after the function returns?

No — and this is worth flagging even though this module doesn't demonstrate the failure. Once demo()/main() returns, the stack space for x, y, and arr is considered free again and can be overwritten by the next function call. A pointer to it becomes a dangling pointer — this course earns that term properly once Module 05's linked list can delete a node and actually demonstrate the failure, rather than just naming it.

Why didn't the Python demo need to "free" anything, when the C and C++ versions didn't either (there's no free()/delete anywhere in this module)?

Every value in this module's C and C++ demos lived on the stack (see variables-and-memory) — plain ints and a fixed-size array, none of it heap-allocated, so there was nothing to free. This module intentionally stays on the stack throughout; heap allocation (and the cleanup it requires) is introduced in Module 03, once there's a real reason to need memory whose size isn't known until runtime.
