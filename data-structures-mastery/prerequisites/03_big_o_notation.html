Prerequisite 03 of 04

Reading Big-O Notation

Not how to derive Big-O (that's earned properly in Module 04) — just how to read it fluently, since every module from here on states one.

01

The Big Analogy

Looking for a name in a phone book vs. a shuffled pile of index cards. Say you need to find "Wilson" in a phone book of 1,000,000 names. If it's alphabetized, you open to the middle, see you're past "W," flip back to the middle of what's left, and so on — about 20 flips, tops. Double the phone book to 2,000,000 names and you need only one more flip. That's how forgiving a good structure can be.

Now say the same 1,000,000 names are on index cards in a random pile. You have to check cards one at a time until you get lucky. Double the pile, and on average you double your work. Big-O notation is just a compact way of saying "which of these two situations are we in, and how bad does doubling the input make it?" — without caring about the exact number of flips, only the shape of how the work grows.

02

What Happens, Step by Step

  1. Count the operations that matter as a function of input size n — comparisons, swaps, array accesses; whichever operation dominates the work for the structure/algorithm in question.
  2. Throw away constants and low-order terms. "5n + 12 operations" and "n operations" are both written O(n), because what Big-O communicates is growth shape, not an exact count — the constants get swamped as n gets large, and different machines/languages have different constants anyway.
  3. Name the shape using the table in section 04 below — O(1), O(log n), O(n), O(n log n), O(n²) are the five you'll see constantly in this course.
  4. State which case you mean. "Big-O" technically means worst case, but this course (and most working programmers) also talks about average case and best case for the same structure — a hash table is O(1) average but O(n) worst case, and both facts matter. Modules will always say which one they mean.

The jump from O(n log n) to O(n²) at real scale is why Module 31 proves a lower bound before any sort is written — so you know 20,000,000 vs. 1,000,000,000,000 isn't a rounding error, it's the entire reason merge sort exists.

04

Time vs. Space — the Other Axis

Everything above described time complexity — how the number of operations grows. The exact same notation also describes space complexity — how much extra memory an algorithm needs beyond its input. Merge sort (Module 33) is O(n log n) time but O(n) space, because it needs a second array to merge into. Heap sort (Module 35) is also O(n log n) time, but O(1) space, because it sorts in place. Whenever this course states a complexity with no axis named, assume time — space is always called out explicitly.

  • The time/space distinction so a module can say "O(n) space" without re-explaining it
One confusion to kill early

O(n²) is not automatically "bad" and O(n) is not automatically "good." For small n, a simple O(n²) algorithm with tiny constants can beat a fancy O(n log n) one with large constants — which is exactly why real sorting libraries fall back to insertion sort (Module 32) for small sub-arrays inside an otherwise O(n log n) sort. Big-O describes what happens as n grows large, not what's fastest at every size.
